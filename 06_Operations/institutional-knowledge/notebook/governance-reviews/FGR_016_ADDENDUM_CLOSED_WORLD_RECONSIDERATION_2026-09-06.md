## 1. The governed proposition is preserved, not reopened

**(A) Primary evidence — unchanged.** Re-read directly from `FGR_016` §2–§3 and the `GOVERNED-CLAIMS.md` entries: Pika's Free tier is restricted to personal, non-commercial use; Standard, Pro, and Fancy paid tiers carry commercial-use rights, undifferentiated among the three, per the twice-independently-fetched pricing page and the corroborated (not fully-fetched) Terms of Service excerpt. No tier beyond these four is evidenced anywhere in the FGR's own record.

**(B) Governed proposition — unchanged.** The Free-versus-paid distinction FGR_016 adopted remains the correct statement of Pika's terms. The `not_equals 'Free'` defect is a representation problem in how that distinction was encoded, not evidence the distinction itself is wrong — consistent with, and not reopening, `FGR_016_ADDENDUM_APPLICABILITY_SAFETY_2026-09-05.md` §2's own classification.

## 2. The closed-world invariant, derived from first principles

The qualifying condition must mean: *the canonicalized `tool_plan_tier` value is one of the specific evidence-supported qualifying tiers* (`Standard`, `Pro`, `Fancy`) — never *the tier is anything other than `Free`*. Required behavior, worked through case by case:

- Recognized qualifying tier (`Standard`/`Pro`/`Fancy`, post-canonicalization) → may satisfy the condition.
- Recognized `Free` (post-canonicalization, including the aliases `aba157bc` already covers) → must not satisfy it.
- Unknown/unrecognized tier (including any future Pika tier not in evidence) → must not satisfy it.
- Missing/unconfirmed fact → `unresolved`, never guessed.
- Ambiguous generic wording ("paid", "premium", "business") → must not be inferred into any specific qualifying tier; remains unmatched, `unresolved`/`not_met` as the evaluator's existing fallthrough already produces for any value that doesn't canonicalize to a known term.

This is the same NORMALIZATION-vs-CANONICALIZATION-vs-INFERENCE distinction the prior architecture review derived: legitimate canonicalization maps a closed set of known-equivalent phrasings to a governed value; it must never guess a specific tier from generic paid-language.

## 3. Representation options, assessed against the actual current schema/evaluator (not assumed)

**Option A — multiple `equals` requirements on one claim, relying on AND-combination to express OR.** Read directly at `aba157bc`: `evaluateApplicabilityDetailed` maps every requirement in `applicability_requirements: ApplicabilityRequirement[]` to an outcome, and `isApplicable`/downstream `RetrievalResult` construction requires **every** outcome to be `'met'` (`.every((o) => o.status === 'met')`) — confirmed AND-only, no OR/IN semantics exist anywhere in this evaluation path. `tool_plan_tier` is a single `Attested<string>` value (`ToolMention.plan_tier`) — it cannot simultaneously equal `'Standard'` AND `'Pro'` AND `'Fancy'`. Three ANDed `equals` requirements on one claim would make that claim's applicability gate permanently, structurally unsatisfiable. **Rejected — proven impossible, not merely undesirable.**

**Option B — separate governed claims per qualifying tier, using existing `equals` semantics.** Three claims, each carrying the identical baseline-plus-exception proposition text already adopted, differing only in a single applicability requirement: `{ fact: 'tool_plan_tier', tool: 'pika', operator: 'equals', value: 'Standard' }`, `...value: 'Pro'`, `...value: 'Fancy'`. Assessed on the merits, not rejected for claim-count alone:
- **Retrieval/duplication:** `tool_plan_tier` is single-valued per tool mention — at most one of the three claims' applicability requirements can ever be `met` at a time (the other two are structurally `not_met`, since `actual` cannot equal two different canonical values simultaneously). No duplicate-result risk exists; this is the same single-valued-fact property that made Kling's/Runway's baseline-plus-exception pairs safe.
- **Composition:** each claim's proposition text is identical (verbatim from FGR_016), so whichever one claim resolves `met` renders exactly the adopted proposition — no new Composition logic, no Pika-specific rendering.
- **Provenance:** all three would cite the same FGR_016 evidence and the same primary sources; a `Related`-style cross-reference (mirroring the Stock Editorial `[[...]]` convention) would tie them together as one evidenced proposition split across three claim identities.
- **Future tier addition:** a genuine, disclosed maintenance cost — a new Pika paid tier would require its own new claim plus its own FGR/CPR cycle (this is a real, non-trivial burden, but not a safety defect; it is the direct, honest cost of a closed-world representation using only existing machinery, and is exactly the trade-off closed-world safety requires).
- **Claim identity/maintainability:** three claim IDs to track instead of one, but each is individually simple (single `equals`, no compound logic).
Assessed as **safe and fully representable with existing, unmodified machinery.**

**Option C — a new `one_of`/`IN` operator.** Read directly: `ApplicabilityRequirement.operator: 'equals' | 'not_equals'` only (`types.ts` line 188); no array/set-membership operator exists anywhere in the schema or evaluator. Corpus-wide check (`grep` across all of `GOVERNED-CLAIMS.md` and `topic-claims-fixture.ts`): **zero existing governed claims use more than a single applicability requirement**, and none has ever needed multi-value matching — the demand for `one_of` is entirely hypothetical, not evidence-backed, exactly as the prior architecture review's Part 7 found. Adding an operator here would also not, by itself, resolve the canonicalization dependency (a `one_of: ['Standard','Pro','Fancy']` evaluated with the same raw-string logic would still need casing/alias canonicalization for each of the three values, exactly as Option B does) — so it would not shrink the total work, only relocate it into a schema/evaluator change with no current second use case to justify it. **Assessed as a genuine but currently unnecessary generic capability — not required to solve this instance.**

**Option D — another existing generic representation.** `jurisdiction`'s `AssessmentJurisdictionFacts` (`included`/`excluded` membership lists) was considered as a possible reusable set-membership pattern, but is structurally inapplicable here: it exists because assessment jurisdiction is a genuine cardinality-many fact (multiple jurisdictions can simultaneously apply to one project); `tool_plan_tier` is a single-valued attested fact per tool mention, with no analogous multi-membership model anywhere in the current type system. No other existing generic representation was found. **Not applicable.**

## 4. Generic architecture test

Option B requires no Composition special-casing of Pika tier names (Composition renders only the shared, already-adopted proposition text, identical across all three claims), no Retrieval special-casing (the existing per-tool `equals` lookup path, already exercised for `tool_account_status`, is reused unmodified), no question-generation special-casing (askability remains untouched — see §6), and no inference from generic "paid" wording into a specific tier (each claim's requirement names its own specific evidenced tier explicitly; ambiguous wording simply fails to canonicalize and the requirement remains `unresolved`/`not_met`, never guessed). **Determination: A — existing architecture can safely represent the proposition today; no new generic capability is required.**

## 5. Canonicalization interaction — a real, disclosed dependency of Option B

`aba157bc`'s `CATEGORICAL_VALUE_ALIASES` table today contains **only** Pika's Free-tier aliases (`free`, `free tier`, `the free plan` → `Free`). It does **not** yet contain entries mapping casing/wording variants of `Standard`, `Pro`, or `Fancy` to their canonical forms (e.g. `standard`/`the standard plan` → `Standard`). Under Option B, each of the three new claims' `equals` comparison would, without such entries, only match the exact capitalized strings `'Standard'`/`'Pro'`/`'Fancy'` — safe (fails closed to `not_met`/`unresolved` on any variant, never incorrectly grants the exception), but less complete than it could be. **This reconsideration explicitly does not authorize adding those alias-table entries** — that is data-authoring work belonging to whatever future task actually implements the corrected representation (mirroring how the existing Free-tier aliases were authored directly from FGR_016's own evidence, not invented generically), not this read-only reconsideration. The dependency is disclosed, not resolved, here.
